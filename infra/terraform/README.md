# Operonix — Terraform (Google Cloud infrastructure)

Minimal, deliberately small module for the Operonix platform resources: Artifact Registry, Cloud SQL
PostgreSQL 16, Secret Manager, the runtime service account with least privilege, Cloud Run service
and migration job, plus optional Cloud Storage and GitHub Workload Identity Federation.

**Nothing here has been applied.** Applying it creates billable Google Cloud resources; do it only
with the explicit approval of the project owner.

```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars    # then edit project_id / region / environment
terraform init
terraform validate
terraform plan      # review every resource and its cost implication before applying
terraform apply
```

## Layout

| File | Contents |
| --- | --- |
| `versions.tf` | Provider requirements, optional GCS backend for shared state |
| `variables.tf` | Inputs and safe defaults (region defaults to `asia-south1`) |
| `platform.tf` | Artifact Registry, Cloud SQL, secrets, service accounts, optional bucket and OIDC |
| `run.tf` | Cloud Run v2 service (probes, secrets, Cloud SQL socket) and migrate-only job |
| `outputs.tf` | Service URL, connection name, secret IDs, CI identity values |
| `terraform.tfvars.example` | A working example for staging |

## Relationship to the CLI scripts

| Concern | Owner |
| --- | --- |
| Provisioning infrastructure | Terraform (`infra/terraform`) or `deploy/gcp/deploy.sh` / `.ps1` bootstrap |
| Building and shipping a revision | Cloud Build + `deploy/gcp/deploy.sh` / `.ps1` deploy, or `.github/workflows/deploy.yml` |

Both paths converge on the same resources. Pick one: `terraform apply` plus the deploy scripts, or
the scripts' own `bootstrap` command. Running both against the same project will conflict.

`run.tf` intentionally ignores changes to `template[0].containers[0].image` (and `client*`), so
Terraform does not fight the deployment pipeline for control of the running revision. Terraform
manages the *shape* of the service — sizing, secrets, probes, Cloud SQL attachment — and the scripts
manage the *image*.

## Cost notes

* Cloud SQL is the dominant cost and runs continuously. Use `db-g1-small` for staging, a
  `db-custom-*` tier for production, and delete staging instances when they are not needed.
* Cloud Run with `min_instances = 0` costs nothing while idle; `startup_cpu_boost` only bills during
  startup.
* `create_attachments_bucket = false` by default: no bucket is created until file storage is
  implemented.
* Artifact Registry keeps the most recent 10 tagged images.

## Secrets

Database passwords and the JWT signing key are generated by Terraform, stored as Secret Manager
versions and referenced by name only. They are never written to the repository, to outputs, or to
the container image, and Terraform marks the plaintext attributes as sensitive (they remain in
state, which is why remote state with restricted access is recommended).
